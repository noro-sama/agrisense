Act as a Senior Node.js Engineer. I am building Agrisense, an agricultural decision
engine for smallholder farmers in Zambia, for the Meta Global AI Developer Hackathon.

WHAT IT DOES
Farmers message Agrisense on Telegram with their district and crop. The system fetches
localised weather, computes agronomic features server-side, then asks a Meta Llama model
to reason ONLY over those pre-computed numbers and return a structured planting decision.
A human farmer makes the final call; the system informs it.

NON-NEGOTIABLE PRINCIPLES
1. The LLM never sees raw API payloads and never invents numbers. It receives only
   computed features and must cite nothing outside them.
2. Every LLM output is validated against its input before being returned. If the model
   names a rain date when the features show no effective rain, override it.
3. Data provenance is visible. Every response states which sources informed it.
4. Graceful degradation always. If any dependency fails, return honest partial advice
   labelled as such, never a generic error.

DATA SOURCES
AgriRigo public API. Base URL: https://api.agririgo.com/api/v1 . No auth required. Rate limited.

USE ONLY THESE ENDPOINTS (hardcoded in /data/agririgo-endpoints.json):
- GET /weather/live?lat={lat}&lon={lon} → Current + 7-day forecast. Cache 15 min.
- GET /soils?province={name} → WRB soil groups, pH, constraints. Cache 90 days.
- GET /districts?province={name} → 44 districts with zone, key crops, drought severity.
  Use ONCE at startup to validate district map, then use local /data/districts.json.
- GET /drought/2024?province={name} → Historical 2023/24 impact. Use for context only,
  NOT as current El Niño status. Label clearly as "last season's data".

DO NOT USE:
- /production, /food-security, /indicators, /ias-2024, /africa (structural data)
- OpenWeatherMap (superseded by /weather/live)
- Any endpoint not explicitly listed above

CRITICAL RULES:
1. Respect cache_ttl_hours exactly. Never refetch within TTL window.
2. If params missing/invalid, return error to user. Never guess defaults beyond docs.
3. Fields marked 'model-estimate' MUST be labeled indicative, not official statistics.

LOCATION RESOLUTION
No geocoding API. Use /data/districts.json: a curated flat map of ~40 major Zambian
agricultural districts with lat, lon, province, plus an aliases map and a default
(Lusaka). Normalise input by lowercasing, trimming, stripping suffixes like "town".
Resolve exact match, then alias, then substring. Always return a matched boolean.
When unmatched, the Telegram reply MUST state that a default location was used and
invite the user to reply with their district.

FEATURE COMPUTATION
Input is AgriRigo daily arrays. Compute per day index:
- rain_next_5d_mm: sum of precipitation_sum[0..4]
- has_effective_rain_in_window: any day where precipitation_sum >= cropThreshold
- first_effective_rain_date: matching date string, else 'none_within_forecast_window'
- heavy_rain_risk_days: count of days where precipitation_sum >= 25
- heat_stress_days: count where temperature_2m_max >= 35
- dry_streak_days: leading consecutive days with precipitation_sum == 0
- best_confidence_for_first_effective_rain: precipitation_probability_max on that date
- window_through: last date in array
Pass confidence into the AI prompt so the model can downgrade its own confidence when
probability is below 50%. Never present a low-probability forecast as certain.
Maize, beans, groundnuts, soybean each get their own minimum effective rainfall and
waterlogging sensitivity. My brother lost a bean crop to heavy rain — beans are
sensitive to waterlogging, so encode that.

AI SERVICE CONTRACT
Input: { features, cropKnowledge, soilData }
Output JSON schema:
{
  "recommendation": "PLANT | WAIT | HARVEST_WINDOW",
  "confidence": "high | medium | low",
  "reason_plain": "one sentence, plain language",
  "timing": "specific date range, or 'no planting window in current forecast'",
  "risk_flags": ["short strings"],
  "context_notes": ["Last season drought: severe (historical)", "Soil: sandy loam"],
  "sources_used": ["agririgo:weather-live"]
}
System prompt rules: reason only from supplied features; never fabricate dates or
rainfall figures; if has_effective_rain_in_window is false, recommendation must be
WAIT and timing must state no window exists; prefer WAIT when confidence would be low;
if heavy_rain_risk_days > 0 and the crop is waterlogging-sensitive, flag flood risk
explicitly.
Retry once on malformed JSON using a stricter corrective prompt. On second failure,
return rule-based advice derived from features with confidence "low".

TELEGRAM FLOW
Parse `message.text` and `chat.id`. Extract district and crop via simple keyword matching
(not an LLM call). Default location: Lusaka. Default crop: Maize.
Call services in order, format result as short Telegram-friendly text (under 600 chars,
plain text with line breaks), send via bot.sendMessage().
Handle /start command with a welcome message.

CACHING (utils/cache.js)
Generic TTL Map keyed by resource+params. Weather 15 min, soils 7 days.
On upstream failure serve stale cache entry with a "stale_data" flag rather than failing.

RESPONSE BUDGET
Target end-to-end under 8 seconds. One Meta API call per message.

BACKTEST SCRIPT (scripts/backtest.js)
Pull actual daily rainfall from Open-Meteo archive for 4 Zambian provinces covering
Oct 2024 – Mar 2025. Report four metrics: effective-rain precision, false-WAIT rate,
MAE on weekly totals, MAE on timing. Output to /data/backtest_results.json.
